# AI Developer setup (OpenRouter)

The AI endpoint is a Vercel serverless function at `/api/ai-developer`. It is disabled (503) unless all configuration and its distributed quota database are available. Never put secrets into client-side code, Git, or chat.

1. Revoke any OpenRouter key that was shared publicly or in chat. Create a replacement and set strict OpenRouter credit/spend limits. Use a model supported by OpenRouter's JSON response format.
2. Run `supabase/migrations/20261012_ai_developer_quota.sql` in the site's Supabase project. It creates a server-only quota table and a service-role-only RPC; it does not alter existing tables. The RPC uses row locks for atomic limits across Vercel instances. It permits at most 5 requests per IP per minute and 100 total requests per rolling day. Failed provider calls also consume quota. This is abuse reduction, not user authentication or a spending guarantee. Set provider credit limits and consider Vercel Firewall controls; anyone can use the public endpoint within the quota. Hashed IP buckets persist; arrange periodic deletion of old `client:` rows if retention is not desired.
3. In the Vercel project environment settings, add these **server-only** variables for each relevant environment:
   - `OPENROUTER_API_KEY`: the replacement OpenRouter key.
   - `OPENROUTER_MODEL`: optional; defaults to `openai/gpt-4o-mini`.
   - `AI_LIMIT_SUPABASE_URL`: URL of the Supabase project containing the migration (e.g. `https://<project>.supabase.co`).
   - `AI_LIMIT_SUPABASE_SERVICE_ROLE_KEY`: that project's service role key (not the publishable/anon key).
   - `AI_RATE_LIMIT_SECRET`: a random secret at least 32 characters long, used to HMAC IP addresses for quota buckets. Rotating it resets per-IP buckets.
4. Redeploy after setting variables. No secrets should be prefixed `NEXT_PUBLIC` or added to `rsbuild.config.ts`. Check the feature from the deployed site; the plain Rsbuild dev server does not run Vercel functions. For local end-to-end testing use a Vercel-compatible local function runner and local environment variables; never commit them.

Messages are sent to OpenRouter and the selected model provider. They are held only in page state by this feature and are not intentionally logged or saved by the server. Refer to the providers' own retention policies. The service uses same-origin POST, limits input, fails closed if quotas are unavailable, and filters common token patterns, but this is not a substitute for never entering credentials in chat.

The AI generates a validated, deliberately limited structured specification, not arbitrary executable code or XML. The site compiles it locally using existing Blockly blocks. If the model's first structured response fails validation, the server makes one repair request naming the exact problem (for example a missing key or a wrong type) and returns the corrected draft when it validates; the repair counts against the same single quota unit. If both attempts fail, the chat shows the model's reply text so the conversation can continue instead of ending in an error. Supported drafts buy one contract per cycle, with either instant/latest-exact-digit entry or an ordered list of entry rules; the first matching rule chooses that cycle's contract and barrier, and cycles with no match wait for the next tick. Rule conditions cover digit streaks, over/under/matches/differs runs, parity and over/under shares, rising/falling tick runs, exact digits and AND/OR groups. A strategy may instead buy a simultaneous two-leg hedge: both legs are bought on the same tick with the full stake each, both legs must share a category (both digit or both Rise/Fall), both predictions are explicit, and the cycle result is the combined profit of the pair. The AI must warn that a Rise + Fall pair wins one leg and loses the other, so after the payout spread each cycle normally nets a loss (and an unchanged price can lose both legs), and obtain explicit confirmation before drafting one; martingale then doubles both stakes. Fixed/martingale stake, optional recovery prediction and post-settlement TP/SL are supported. AI drafts also support a virtual hook — for a single one-tick digit contract, for multi-rule strategies whose rules all buy digit contracts, or for a paired hedge (Rise/Fall pairs at any tick duration, digit pairs with one tick) — that starts virtual, switches to real after either a configured number of consecutive virtual losses or consecutive virtual wins, and returns to virtual after a real loss without resetting the real stake. Virtual outcomes are live-tick simulations, not real purchases and may differ from actual contract execution. Other virtual rules, more than two contracts per cycle, hedge legs from different categories, hedge combined with rules, arbitrary custom code, indicators outside the listed conditions, more than one contract per cycle, more than 12 rules, and fresh-tick entry requirements remain unsupported and must be explained instead of silently approximated. Review every setting in Bot Builder and test on a demo account. Generated drafts do not start trades automatically; TP/SL is checked after settlement and may be exceeded. Market and contract availability, minimum stakes, execution and provider output still need real-world verification.
